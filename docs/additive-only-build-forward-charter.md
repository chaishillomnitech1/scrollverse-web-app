# Additive-Only Build-Forward Charter

**Status:** Active working addendum  
**Added:** 2026-11-10  
**Applies to:** ScrollVerse, Omnitech1, Atlas Core, the Story Archive, connected repositories, creative systems, and future integrations.

> This document is an additional operating layer. It does not replace, rewrite, summarize away, or supersede any earlier manifesto, blueprint, conversation, artifact, technical decision, symbolic language, or project record.

## 1. The governing rule

**Preserve everything. Add to the foundation. Keep building.**

The user's explicit direction is:

> “Don't remove nothing from my builds ... we add on to the foundation ...”

The assistant's matching commitments are:

- Preserve, don't erase.
- Expand, don't dilute.
- Integrate, don't replace.
- Document, don't rewrite history.
- Keep original material intact and recoverable.
- Add new capabilities in distinct layers.
- Append corrections with dates and reasons; never silently replace the original.
- Keep alternative interpretations side by side with the source rather than substituting one for the other.
- Do not delete, simplify, rename, flatten, or replace architecture without explicit authorization.
- Connect every new integration to the existing foundation.

Symbolic, experimental, visionary, unconventional, or incomplete material remains part of the record. Technical status notes may be added alongside it; they do not erase its original meaning.

## 2. Build-forward means execution, not endless preflight

The user's direction is to stop circling around already-established work and move into productive building.

The default operating loop is:

1. **Locate** the existing artifact, code path, decision, or integration before proposing anything new.
2. **Understand** its current structure and its links to the wider system.
3. **Extend** the existing foundation with the smallest coherent additive change.
4. **Build and test in the same workstream.** Validation is part of engineering, not a recurring reason to postpone implementation.
5. **Record** the changed files, commit, test results, deployment evidence, and any remaining blocker.
6. **Continue** to the next useful build task without reopening settled questions.

Do not repeatedly ask the user to re-prove facts already present in the conversation, repository, or connected records. Do not turn every response into another plan, audit proposal, checklist, or request for permission to do ordinary reversible work.

A check is useful when it answers a concrete engineering question, protects an irreversible boundary, or catches a real regression. Once answered, record the result and move forward.

These are starting points to inspect and extend—not invitations to create duplicate portals, registries, chronicles, or archives. Preserve existing routes, components, identifiers, records, and original language. Add connections and capabilities where they fit.

## 4. Source integrity and evidence

Preserve the distinction between:

- Original conversation or artifact.
- User-provided description or metric.
- Assistant-generated interpretation.
- Implemented code or committed documentation.
- Automated test result.
- Deployment or runtime evidence.
- External transaction, adoption, or real-world outcome.

These distinctions make the archive stronger; they do not diminish creative intent. Missing evidence stays marked as missing until it is recovered. A proposal is not silently promoted to a completed deployment, and a later correction does not delete the earlier record.

For conversation recovery, retain original titles, conversation IDs, timestamps, message history, attachments, source platform, artifact connections, repository references, and recovery status whenever the source provides them. Candidate titles remain candidates until matched to the export or original screenshot. The available ChatGPT export and existing recovery index are working source material, not proof that every conversation has already been recovered.

## 5. Boundaries that remain protected

Build-forward does not mean making irreversible changes without authority. The following remain separate protected actions:

- Deleting or overwriting original material.
- Changing repository visibility or access.
- Publishing private conversations or source records.
- Applying database migrations, seeding production data, or publishing ingested records.
- Signing wallets, moving funds, changing financial settings, or executing external transactions.
- Production deployment when an explicit owner or release approval is required.

For these boundaries, continue all safe additive preparation and implementation work. Ask only for the specific approval that is genuinely required; do not use the boundary as a reason to stop unrelated progress.

## 7. The response standard

When the user asks to build:

- Do the useful work now when the connected tools and available permissions allow it.
- State what was actually changed and provide the commit, PR, test, or deployment evidence.
- If blocked, identify the exact blocker and continue with the safe work that remains possible.
- Do not claim an action succeeded unless the tool or system returned evidence.
- Do not end with a generic menu of next steps when there is a concrete build task to execute.
- Do not make the user repeat the project's history when relevant context or source records are already available.

**The standard is productive continuity: preserve the origin, connect the work, build the next layer, and keep moving.**
